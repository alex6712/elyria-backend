# ADR-0009: Общая проверка access-токенов между bounded contexts

## Статус

Accepted

---

## Контекст

Приложение развивается по модели нескольких bounded contexts (сейчас: Users, Observability; планируются Media, Couples, Notes и др.). Access-токены выпускаются контекстом Users (JWT, Ed25519, issuer = имя приложения, утверждения `sub`, `exp`, `iat`, `jti`, `sid`), а потребляться будут конечными точками всех остальных контекстов.

До принятия данного ADR проверка токенов была полностью локализована в контексте Users:

- порт `TokenVerifier` и DTO `TokenClaimsDTO` — в `src/users/application/`;
- реализация `JwtTokenVerifier`, провайдер ключей `SignatureKeysProvider` — в `src/users/infrastructure/`;
- хранилище отозванных токенов `TokenBlacklist` (Redis) — тоже в Users;
- исключения токенных ошибок и их 401-обработчики — в Users;
- составные фабрики (`build_token_verifier`, `build_token_blacklist`, `build_signature_keys_provider`) — в `src/users/composition/services.py`.

При этом выявлены две проблемы:

1. **Дублирование при появлении новых контекстов.** Каждый новый BC, принимающий access-токен, вынужден повторять порт, адаптер, исключения, обработчики и фабрику, либо нарушать границы слоёв, импортируя код из Users.
2. **Проверка отзыва не включена ни в один путь запроса.** `TokenBlacklist.is_revoked()` не вызывается нигде: отзыв access-токена при logout не оказывает эффекта на последующие запросы с этим токеном.

Необходимо определить единый механизм проверки access-токенов для всех bounded contexts, включая проверку статуса отзыва.

---

## Требования

1. **Соответствие Clean Architecture** — порты остаются в Application Layer, адаптеры — в Infrastructure (ADR-0008).
2. **Автономия bounded contexts** — BC не импортируют друг друга и не зависят от глобального Composition Root (ADR-0001, правило «не ходить наверх»).
3. **Явность важнее магии** — проверка отзыва остаётся явной операцией, а не скрытым побочным эффектом криптографической проверки.
4. **Тестируемость** — порты и адаптеры заменяемы при тестировании.

---

## Рассматриваемые варианты

### Вариант A: Каждый BC повторяет паттерн Users

Каждый новый контекст реализует собственный порт `TokenVerifier`, адаптер `JwtTokenVerifier`, хранилище отзыва и фабрики; публичный ключ передаётся параметром из глобального Composition Root.

#### Преимущества

- Полная автономия BC: контексты не делят код.
- Ноль изменений в `src/shared/` и контрактах import-linter.

#### Недостатки

- Дублирование ~140 строк на каждый BC.
- Риск расхождения реализаций (алгоритм, issuer, набор обязательных утверждений, семантика ошибок).
- Проблема «забытой» проверки отзыва воспроизводится в каждом новом контексте.

#### Влияние на безопасность

Негативное: единая политика проверки токенов не зафиксирована; каждая реализация может отличаться.

---

### Вариант B: Проверка отзыва внутри `TokenVerifier.verify`

Реализация `JwtTokenVerifier` дополнительно проверяет `TokenBlacklist.is_revoked(jti)` при каждом вызове.

#### Преимущества

- Проверка отзыва гарантирована для всех вызовов `verify()`.

#### Недостатки

- **Смешение ответственности**: криптографическая проверка токена смешивается с проверкой runtime-состояния (Redis).
- **Затрагивает refresh-путь**: тот же `JwtTokenVerifier` проверяет refresh-токены при ротации сессии, а в Redis-blacklist попадают только access-токены; механизм отзыва refresh-токенов реализован через ротацию `session_secret` в БД. Требуется параметр «тип токена», возвращающий проблему «можно забыть».
- **Redis становится обязательным** для любой проверки токена, включая refresh-путь.

#### Влияние на безопасность

Позитивное по покрытию, но негативное по предсказуемости: отказ Redis ломает аутентификацию целиком.

---

### Вариант C: Общий механизм в `src/shared/`

Порты, DTO, исключения и адаптеры проверки токенов переносятся в `src/shared/`. Use cases каждого BC потребляют общие порты `TokenVerifier` и `TokenBlacklist`, явно выполняя проверку отзыва после проверки подлинности. Составные фабрики общих ресурсов размещаются в глобальном Composition Root (`src/composition/security.py`), как и фабрики других общих ресурсов (`engine.py`, `redis.py`).

#### Преимущества

- **Единый код**: один порт, один адаптер, одна семантика ошибок и 401-ответов для всех BC.
- **Refresh-путь не затрагивается**: синхронный `TokenVerifier` остаётся чистым криптографическим контрактом и продолжает использоваться для refresh-токенов.
- **Явность**: проверка отзыва — отдельный явный шаг в use cases (вызов `TokenBlacklist.is_revoked`), а не скрытый побочный эффект.
- **Соответствие ADR-0001**: общие ресурсы (ключи, Redis) создаются в глобальном Composition Root и передаются параметрами в фабрики BC.

#### Недостатки

- `src/shared/` получает первые security-адаптеры: риск «god package» при отсутствии дисциплины.
- `TokenClaimsDTO` становится общим контрактом: изменения утверждений затрагивают все BC.
- Необходим перенос существующего кода Users и обновление контрактов import-linter.

#### Влияние на безопасность

Позитивное: единая политика проверки токенов, гарантированная проверка отзыва, единое отображение токенных ошибок в 401.

## Рекомендация

Рекомендуется **Вариант C**.

Обоснование:

1. Access-токен — общий технический контракт между контекстами: выпускается Users, потребляется всеми. Единая реализация проверки соответствует принципу максимального переиспользования (AGENTS.md, п. 5).
2. Размещение составных фабрик в `src/composition/` соответствует ADR-0001 (дополнение, п. 3): ключи подписи и Redis-клиент — общие ресурсы, создания которых BC не должны дублировать.

---

## Решение

Принят **Вариант C**.

### 1. Размещение компонентов

В `src/shared/` размещаются:

- `src/shared/application/dto/token_claims.py` — `TokenClaimsDTO`;
- `src/shared/application/ports/security/token_verifier.py` — порт `TokenVerifier` (синхронный, криптографическая проверка);
- `src/shared/application/ports/persistence/token_blacklist.py` — порт `TokenBlacklist`;
- `src/shared/application/exceptions.py` — `TokenExpiredError`, `TokenSignatureInvalidError`, `TokenInvalidError`, `TokenRevokedError`;
- `src/shared/infrastructure/adapters/security/jwt_token_verifier.py` — `JwtTokenVerifier`;
- `src/shared/infrastructure/signature_keys_provider.py` — `SignatureKeys`, `SignatureKeysProvider`;
- `src/shared/infrastructure/adapters/persistence/redis_token_blacklist.py` — `RedisTokenBlacklist`;
- `src/shared/presentation/http/handlers/client/unauthorized.py` — 401-обработчики токенных исключений (регистрируются в общем `register_exception_handlers`).

### 2. Проверка отзыва

Проверка отзыва выполняется в use cases каждого BC явным вызовом `TokenBlacklist.is_revoked` сразу после проверки подлинности:

```python
claims = self._token_verifier.verify(token)
if await self._token_blacklist.is_revoked(claims.token_id):
    raise TokenRevokedError(...)
```

Use cases получают `TokenVerifier` и `TokenBlacklist` отдельными параметрами. Проверка отзыва не включается в синхронный `TokenVerifier`, используемый refresh-путём.

### 3. Составной корень

Фабрики общих ресурсов размещаются в `src/composition/security.py`:

- `build_signature_keys_provider` — загрузка ключей Ed25519;
- `build_token_verifier` — проверка подлинности токенов;
- `build_token_blacklist` — хранилище отозванных токенов (Redis).

Глобальный Composition Root создаёт ключи и сервисы один раз и передаёт их параметрами в фабрики модулей BC (`build_users_module` и будущие). BC не импортируют `src.composition` (контракт `users-does-not-depend-on-composition` сохраняется).

### 4. Шаблон для будущих bounded contexts

Новый BC, принимающий access-токен:

- получает `token_verifier` и `token_blacklist` параметрами своей фабрики модуля из глобального Composition Root;
- вызывает `TokenVerifier.verify()` и `TokenBlacklist.is_revoked()` в своих use cases;
- токенные ошибки отображаются в 401 общими shared-обработчиками без дополнительного кода.

### 5. Документация

Настоящий ADR фиксирует решение. Содержимое перенесённых компонентов не изменялось, изменено только размещение и импорты.
